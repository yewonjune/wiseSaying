# 명언 앱 (콘솔, Controller · Service · Repository 구조)

Status: ready-for-agent

## Problem Statement

스프링부트의 Controller · Service · Repository 계층 구조를 익히고 싶지만, 웹·스프링을 한꺼번에 배우면 계층 구조 자체에 집중하기 어렵다. 콘솔에서 동작하는 작은 명언 앱으로 "입력 → 컨트롤러 → 서비스 → 리포지터리 → 저장소" 흐름과 계층별 책임 분리를 먼저 연습하고 싶다.

## Solution

IntelliJ + Gradle(Kotlin DSL) + Java 25로 콘솔 명언 앱을 만든다. 사용자는 `등록`, `목록`, `삭제?id=N`, `수정?id=N`, `빌드`, `종료` 명령으로 명언을 관리한다. 명언은 메모리에 보관되고, `빌드`하면 모든 명언이 `data.json`으로 내보내진다. 각 계층은 정해진 책임만 맡는다: 컨트롤러만 입출력하고, 서비스는 순수 비즈니스 로직, 리포지터리는 데이터 생성·조회·수정·삭제만 한다.

목표 출력(명세 예시와 문자 단위로 일치해야 함):

```
== 명언 앱 ==
명령) 등록
명언 : 현재를 사랑하라.
작가 : 작자미상
1번 명언이 등록되었습니다.
명령) 등록
명언 : 과거에 집착하지 마라.
작가 : 작자미상
2번 명언이 등록되었습니다.
명령) 목록
번호 / 작가 / 명언
----------------------
2 / 작자미상 / 과거에 집착하지 마라.
1 / 작자미상 / 현재를 사랑하라.
명령) 삭제?id=1
1번 명언이 삭제되었습니다.
명령) 삭제?id=1
1번 명언은 존재하지 않습니다.
명령) 수정?id=2
명언(기존) : 과거에 집착하지 마라.
명언 : 현재와 자신을 사랑하라.
작가(기존) : 작자미상
작가 : 홍길동
명령) 목록
번호 / 작가 / 명언
----------------------
2 / 홍길동 / 현재와 자신을 사랑하라.
명령) 빌드
data.json 파일의 내용이 갱신되었습니다.
명령) 종료
```

## User Stories

1. 사용자로서, 앱을 실행하면 `== 명언 앱 ==` 제목을 보고 싶다, 그래야 앱이 시작되었음을 알 수 있다.
2. 사용자로서, 매 입력 전에 `명령) ` 프롬프트를 보고 싶다, 그래야 명령을 입력할 차례임을 알 수 있다.
3. 사용자로서, `등록`을 입력하면 내용과 작가를 차례로 입력받고 싶다, 그래야 새 명언을 남길 수 있다.
4. 사용자로서, 등록이 끝나면 `N번 명언이 등록되었습니다.`를 보고 싶다, 그래야 부여된 번호를 알 수 있다.
5. 사용자로서, 첫 명언이 1번이고 이후 1씩 늘어나는 번호를 받고 싶다, 그래야 번호를 예측할 수 있다.
6. 사용자로서, 명언을 삭제한 뒤 새로 등록해도 삭제된 번호가 재사용되지 않길 원한다, 그래야 번호가 명언을 유일하게 가리킨다.
7. 사용자로서, `목록`을 입력하면 `번호 / 작가 / 명언` 헤더와 구분선을 보고 싶다, 그래야 각 열의 의미를 안다.
8. 사용자로서, 목록이 최신 명언부터(번호 내림차순) 나오길 원한다, 그래야 방금 등록한 명언을 바로 확인한다.
9. 사용자로서, 명언이 없을 때 `목록`을 입력하면 헤더와 구분선만 보고 싶다, 그래야 비어 있음을 안다.
10. 사용자로서, `삭제?id=N`으로 특정 명언을 지우고 `N번 명언이 삭제되었습니다.`를 보고 싶다.
11. 사용자로서, 없는 번호를 삭제하려 하면 `N번 명언은 존재하지 않습니다.`를 보고 싶다, 그래야 실수를 알아챈다.
12. 사용자로서, `수정?id=N`을 입력하면 기존 내용을 보여준 뒤 새 내용을, 기존 작가를 보여준 뒤 새 작가를 입력받고 싶다.
13. 사용자로서, 수정 후 목록에서 바뀐 내용과 작가를 보고 싶다.
14. 사용자로서, 없는 번호를 수정하려 하면 아무것도 입력받지 않고 `N번 명언은 존재하지 않습니다.`를 보고 싶다.
15. 사용자로서, `빌드`를 입력하면 모든 명언이 `data.json`에 저장되고 `data.json 파일의 내용이 갱신되었습니다.`를 보고 싶다.
16. 사용자로서, `data.json`이 번호 오름차순 JSON 배열(각 원소 `id`, `content`, `author`)이고 들여쓰기 되어 있길 원한다, 그래야 직접 열어 읽을 수 있다.
17. 사용자로서, 명언이 없을 때 빌드하면 빈 배열이 담긴 `data.json`을 얻고 싶다.
18. 사용자로서, 빌드를 여러 번 하면 `data.json`이 매번 최신 상태로 통째로 덮어쓰이길 원한다.
19. 사용자로서, 내용이나 작가에 `"`, `\`, 줄바꿈이 들어가도 `data.json`이 올바른 JSON이길 원한다.
20. 사용자로서, `종료`를 입력하면 추가 메시지 없이 앱이 끝나길 원한다.
21. 사용자로서, `삭제`나 `수정`에 id를 빠뜨리면 앱이 멈추지 않고 `id를 정확히 입력해주세요.`를 보고 싶다.
22. 사용자로서, id가 숫자가 아니면(`삭제?id=abc`) 같은 안내 메시지를 보고 싶다.
23. 사용자로서, 알 수 없는 명령을 입력하면 `알 수 없는 명령입니다.`를 보고 계속 명령을 입력하고 싶다.
24. 학습자로서, 명령 문자열을 명령 이름과 파라미터로 나누는 일을 한 곳(Rq)에서 하길 원한다, 그래야 스프링의 요청 객체 개념을 연습한다.
25. 학습자로서, 시스템 명령(종료)과 명언 명령(등록·목록·삭제·수정·빌드)을 서로 다른 컨트롤러가 처리하길 원한다, 그래야 도메인별 분리를 연습한다.
26. 학습자로서, 서비스와 리포지터리에 Scanner와 콘솔 출력이 전혀 없길 원한다, 그래야 계층 책임이 분명하다.
27. 학습자로서, 객체 연결을 생성자 주입으로 직접 하길 원한다, 그래야 스프링 DI가 무엇을 대신해 주는지 이해한다.
28. 학습자로서, 예시 시나리오가 자동 테스트로 검증되길 원한다, 그래야 리팩터링해도 동작이 유지됨을 확인한다.

## Implementation Decisions

- **빌드 환경**: Gradle(Kotlin DSL), Java 25(Temurin), IntelliJ IDEA. 외부 런타임 의존성 없음. 테스트 의존성은 JUnit 5, AssertJ.
- **패키지·클래스 구조** (과제의 추천 구조 그대로):
  - `com.back.Main`: App 생성·실행만.
  - `com.back.App`: 메인 루프. `명령) `을 출력하고 한 줄을 읽어 Rq를 만든 뒤 명령 이름에 따라 컨트롤러로 위임. 입출력 가능.
  - `com.back.Rq`: 명령 문자열 파싱. `getActionName()`(`?` 앞부분), `getParamAsInt(name, defaultValue)`(값이 없거나 숫자가 아니면 기본값). 파라미터는 `&`로 여러 개 구분 가능하게.
  - `com.back.domain.system.controller.SystemController`: `종료` 처리. 입출력 가능.
  - `com.back.domain.wiseSaying.controller.WiseSayingController`: 등록·목록·삭제·수정·빌드 응대. 입출력 가능.
  - `com.back.domain.wiseSaying.service.WiseSayingService`: 순수 비즈니스 로직. 입출력 금지. 빌드 시 JSON 문자열 생성과 파일 쓰기 담당(파일 쓰기는 콘솔 입출력이 아니므로 허용).
  - `com.back.domain.wiseSaying.repository.WiseSayingRepository`: 메모리 List 기반 생성·조회·수정·삭제. 입출력 금지. 번호는 `lastId`를 증가시켜 부여(재사용 없음). 단건 조회는 `Optional<WiseSaying>` 반환.
  - `com.back.domain.wiseSaying.entity.WiseSaying`: 번호(id)·내용(content)·작가(author). 수정은 `modify(content, author)` 하나로.
- **객체 연결**: App이 Scanner, 리포지터리, 서비스, 컨트롤러를 직접 생성하고 생성자로 주입. Scanner 하나를 두 컨트롤러가 공유.
- **App 생성자 계약**: Scanner와 data.json 경로를 받는다. Main은 표준 입력 Scanner와 실행 위치의 `data.json`을 넘긴다.
- **종료**: SystemController가 종료 신호를 주면 App 루프가 끝난다. 종료 메시지 없음.
- **오류 처리**: 명세에 없는 메시지는 다음으로 통일.
  - id 누락·비숫자: `id를 정확히 입력해주세요.`
  - 알 수 없는 명령: `알 수 없는 명령입니다.`
  - 없는 번호의 삭제·수정: `N번 명언은 존재하지 않습니다.` (수정은 입력을 받지 않음)
- **입력 검증 없음**: 등록·수정 시 빈 내용/작가도 그대로 저장.
- **data.json 계약**: 번호 오름차순 JSON 배열, 2칸 들여쓰기, 원소 키 순서 `id`, `content`, `author`. UTF-8. 빌드마다 전체 덮어쓰기. 앱 시작 시 data.json을 읽지 않음. JSON은 라이브러리 없이 직접 조립하며 `"`, `\`, 줄바꿈을 이스케이프.
- **저장소 정리**: `git init`, Gradle 기본 `.gitignore`에 `data.json` 추가.

## Testing Decisions

- **테스트 경계는 App 하나.** 테스트는 명령이 담긴 문자열로 Scanner를 만들어 App에 넣고, `System.out`을 가로채 출력 전체를 검증한다. data.json 경로는 `@TempDir` 아래 경로를 넘기고, 빌드 후 파일 내용을 검사한다.
- 좋은 테스트는 외부 동작(콘솔 출력, data.json 내용)만 검증하고, 서비스·리포지터리·Rq·JSON 변환 같은 내부 구조는 직접 테스트하지 않는다. 그래야 내부를 리팩터링하거나 저장소를 바꿔도 테스트가 유지된다.
- 핵심 테스트: 과제 예시 시나리오 전체를 입력하고 출력이 예시와 일치하는지 확인.
- 추가 시나리오: 번호 비재사용, 빈 목록, 없는 번호 수정, id 누락·비숫자, 알 수 없는 명령, 빈 상태 빌드(`[]`), 특수문자 이스케이프, 빌드 덮어쓰기.
- 기존 테스트 선례는 없음(빈 저장소). 이 테스트가 이후 단계의 기준이 된다.
- 도구: JUnit 5, AssertJ.

## Out of Scope

- 파일 기반 영속화(앱 재시작 후 명언 유지), 시작 시 data.json 불러오기.
- 등록·수정 입력값 검증(빈 값 거부 등).
- 검색, 페이징, 정렬 옵션.
- 스프링부트·웹·DB 도입, JSON 라이브러리(Jackson 등) 사용.
- 종료 메시지 등 명세에 없는 부가 출력.

## Further Notes

- 이 단계는 이후 파일 저장 리포지터리, 스프링부트 전환으로 이어질 예정이다. 리포지터리 내부만 바꾸면 되도록 서비스가 리포지터리 구현 세부에 의존하지 않게 유지한다.
- 용어는 `GLOSSARY.md`를 따른다: 명언(WiseSaying), 번호(id), 내용(content), 작가(author), 빌드.
- PC에 JDK가 PATH에 잡혀 있지 않으므로(IntelliJ의 `~/.jdks`에만 있음), 명령줄 실행 시 Gradle 툴체인 또는 IntelliJ의 JDK 설정을 사용한다.
